## Q2 — Will the peak method get brittle for FEM/MDOF/complex systems?
Yes. Peak/feature likelihoods require reliably matching "which peak is which" across the parameter
space. In MDOF/FEM, modes cross, veer, split, and couple; a soft-argmax peak picker becomes ambiguous
and discontinuous (mode-swapping), turning the likelihood multimodal/biased. Whole-PSD/FRF avoids the
identification problem entirely. Conclusion: keep WHOLE-PSD as the default; treat peak-feature as a
studied, labeled comparison only (and expect it to degrade as fidelity rises). This is already the
runners' choice; make it an explicit standing recommendation.

## Q4 — Model-form error: parameter mismatch vs "mesh != reality". How to inject?
Clarification: the current fn/damping mismatch (priors off-truth, build-to-build offsets) is
PARAMETER/epistemic error WITHIN the model family — a 2DOF model can represent it exactly, so inference
recovers it cleanly. That is NOT model-form error. MODEL-FORM error = the true system is OUTSIDE the
inference model's family (the "mesh/FE model is structurally wrong"). Inject by generating the DATA from
a richer/different truth while keeping inference at 2DOF-linear, e.g.:
- add a 3rd mode / extra DOF the inference model lacks;
- amplitude-dependent damping or a Duffing softening term (nonlinearity);
- a frequency-correlated discrepancy added to the true FRF (a GP bias in log-FRF) absent from the model.
Then add a StatFEM GP discrepancy term d(omega) to the inference + a posterior-predictive check, and ask:
does the pipeline DETECT the misfit (discrepancy lights up / PPC p-value fails) or silently absorb it
into biased-but-tight theta? This is round-3 idea #1.

## Q5 — GIF exceedance mismatch (some show spec exceedance, some don't). Why?
Not a physics disagreement; it's band-definition + draws:
- Opus uses the 99%-HI predictive band and reports flight-3 exceeds spec at ~1.2% of frequencies near
  the lower coupled mode (62 Hz).
- Codex uses a q99.5 band + max-ratio metric and reports fully enveloped (max 99%/spec ratio 0.59-0.93).
- Plus different posterior/forcing draws and different peak-frequency resolution (Opus resolves the
  62 Hz coupled peak finely; Codex/Cursor refine at the 86/93 Hz standalone modes — reader §Task2).
DECISION: standardize ONE band definition (recommend symmetric central 99% interval, i.e. q0.5-q99.5,
AND report the one-sided 99%-hi exceedance fraction) before any "spec covers flight" number is quoted.

## Q6 — Why doesn't uncertainty collapse as flights are added?
Two reasons, both real:
1. The structural (epistemic) posterior is already tight after build-0's RICH vibe+modal curves; the 11
   flight observations are scalar 3*GRMS values that carry little structural information, so they barely
   move it (Opus: "posterior stable across cumulative flights"). The toy being same-model means
   epistemic uncertainty was small to begin with.
2. More fundamentally, the GIF bands are PREDICTIVE and include IRREDUCIBLE ALEATORY scatter — fixed
   3 dB flight-to-flight forcing + build-to-build variability. No amount of data shrinks aleatory
   variability; it sets a floor the bands cannot collapse below. So "bands don't collapse" is correct
   behavior, not a bug — but it also shows the sequential-update story is low-value here, and motivates
   reporting the ALEATORY vs EPISTEMIC split (round-3 idea).

## Q7 — Did Cursor cheat on resolution sensitivity?

## Q9 — Build-to-build variability on fn and damping (NEW round-3 spec)
ADD per-structure build-to-build variability on natural frequency and damping: ±5% as the 3-sigma
range for EACH of dome fn, tray fn, dome zeta, tray zeta (so sigma ≈ 1.67% per parameter; lognormal
recommended to keep positivity). Note 5% on fn corresponds to ~10% on stiffness (fn ∝ sqrt(k)). This is
ON TOP of the existing PSD-level build effect. Currently build-to-build is only a PSD-magnitude effect;
this makes each build a genuinely different structure. Record in the round-3 assumptions ledger and
data generator.

## Q10/Q11 — Did the lit review find better assumptions? The 6 dB offset.
- 3 dB flight-to-flight: CONFIRMED reasonable (NASA Yunis, Shuttle+ELV). Keep.
- Sensor noise, build-to-build scale, Matern ell=0.08: NO source pins these — they remain PROJECT
  assumptions. Action: sensitivity-test them or learn them; do not present as standards.
- 6 dB offset: the reader found NO standard for a +6 dB *qualification margin* (GEVS qual margin is
  +3 dB; the +6 dB in GEVS are spectral SLOPES; a +6 dB margin exists only in MIL-STD-464C for EMI/E3,
  not vibration). BUT the human's rationale is legitimate and DIFFERENT: the -6 dB is a PRE-FLIGHT
  CONSERVATIVE DESIGN/QUAL ENVELOPE chosen before any flight data — 6 dB on PSD = 4x PSD = 2x GRMS, a
  standard conservative starting factor. So: KEEP the -6 dB, but label it precisely as a "pre-data
  conservative design envelope (2x GRMS)", NOT as a GEVS acceptance-to-qualification margin. This
  reconciles the framing-challenger critique (it was flagged as "convenient/unjustified"; it now has a
  documented engineering rationale). Still run the sensitivity sweep since the envelope verdict depends
  on it.

## ADDENDUM 2026-06-03 — exceedance reconciliation, Opus QOI gap, runtime, checker audit

### Narrow-band exceedance: reconciliation + the KEY engineering insight
Per-flight numbers (interface response PSD vs the input vibe spec):
- Opus: only FLIGHT 3 exceeds (frac_99hi_exceeds_spec = 0.0118 ≈ 1.2% of freqs near 62 Hz); other 10
  flights 0.0.
- Codex: q99.5 never crosses; worst max_q99.5/spec ratio = 0.93 at 62.4 Hz (~0.6 dB under).
- Cursor: showed it VISUALLY in the GIF but did not quantify (no envelope metric in results.json).
All three are the SAME physical story: the worst-case interface response sits RIGHT AT the spec near
the ~62 Hz coupled mode; whether a given run/flight tips over the line is a draw + band-definition
coin-flip. The human's read is correct: results are close; Opus just tipped over on one flight. This is
NOT a runner discrepancy to litigate — it is the finding.

KEY INSIGHT (human, endorsed — a target result for the problem class): the overall tray 3·GRMS response
(~1 g) is ~44x BELOW the vibe-test level (43.9 g), yet there is a moderate chance of a narrow-band 99%
exceedance at the coupled resonance. So a hugely conservative SCALAR margin can coexist with the tray
being UNDER-qualified in a narrow band. An aerospace org would flag the narrow-band exceedance as a
major risk and ignore the 44x scalar comfort. This is exactly why the PSD-envelope (not the scalar) is
the acceptance check, and it is the spirit of NASA-HDBK-7004 force-limited vibration (spectral truth vs
scalar comfort; resonance-band behavior is what matters). Round 3+ should deliberately design the study
to surface and quantify this (probability of narrow-band exceedance vs scalar margin; tie to force
limiting / notching). This is the most valuable engineering point to emerge so far — make it a headline
objective, not a footnote.

### Checker audit — bottom line (checker_audit.md)
Confirms and sharpens the concern. What is TRUSTED today: only (a) the 4-file immutable hash gate and
(b) named-file existence. Everything substantive (convergence, figure authenticity, no-copied-assets,
runtime honesty, isolation) is SELF-GRADED by runner-authored code. The two hash-locked unit tests
(test_posterior_recovery, test_mdof_transfer) are NEVER EXECUTED by the harness (no config runs them)
and test the LEGACY Metropolis sampler with loose tolerances (0.35 / 0.45). Of five cheat/error modes,
four are uncaught by any trusted control and THREE actually occurred in round 2 (Cursor copied figs;
Cursor runtime understated; Codex ran in master + edited round-1/shared files). Even the best
self-checker (Opus's) has a loophole: its convergence gate sits behind `if converged:`, and the `else`
branch records "honest_not_converged_reported = True" → a NON-converged run still returns all_pass.
Recommended (proposal, needs approval; checker change so between-trials only): five SHARED, hash-locked,
driver-run checks operating on saved bytes, not self-reported JSON —
1) recompute convergence (arviz rhat/ess) over ALL vars from posterior_samples.npz;
2) figure content-hash manifest that FAILS on cross-run byte-identical images unless declared a copy;
3) external wall-clock wrapper (driver holds the clock);
4) key-deliverable presence + frame-distinctness + "not equal to the spec curve" authenticity check;
5) mechanical workspace-isolation guard (sentinel / refuse-if-origin-remote + snapshot-hash round-1 &
   notes). Also: cut/fix/wire the two never-executed unit tests (or stop implying they gate anything).
